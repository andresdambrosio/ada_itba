📘 Capítulo 1

Google Agent Development Kit

ADK es el framework de Google para construir agentes de IA que pueden razonar, usar herramientas y coordinarse entre sí para resolver tareas complejas.

🤖 ¿Qué es un agente?

Un agente es un modelo de lenguaje (LLM) al que le dás un objetivo y un conjunto de herramientas. El modelo decide de forma autónoma qué herramientas usar, en qué orden, y cómo combinar los resultados para lograr el objetivo.

💬

Modelo + Instrucción

El LLM (Gemini) recibe un system prompt que define su personalidad, rol y reglas de comportamiento.

🔧

Tools (herramientas)

Funciones Python que el agente puede llamar: APIs, bases de datos, búsquedas, cálculos, etc.

🔄

Loop de razonamiento

El agente piensa → actúa → observa el resultado → vuelve a pensar, hasta resolver la tarea.

Usuario
→
Agente
(Gemini)
⇄
Tools
(funciones Python)
Razona → Decide → Ejecuta → Observa

El agente decide autónomamente cuándo y qué tool llamar. El usuario solo ve la respuesta final.

🧩 Conceptos clave

1

Agent

El objeto central. Combina un modelo, un system prompt (instruction) y una lista de tools. En ADK se define con LlmAgent.

agent.py 
from google.adk.agents import Agent

root_agent = Agent(
    model="gemini-2.5-flash",
    name="mi_agente",
    instruction="Sos un asistente de...",
    tools=[tool_1, tool_2],
)
2

Tools (herramientas)

Son funciones Python normales con type hints y docstring. ADK las convierte automáticamente en herramientas que el modelo puede invocar. El nombre, los parámetros y el docstring se convierten en el schema que Gemini usa para entender cuándo y cómo llamar cada tool.

tools.py 
def get_order_status(order_id: str) -> dict:
    """Consulta el estado de una orden.

    Args:
        order_id: ID de la orden (ej: 1234567890).

    Returns:
        Estado actual, producto y fecha de entrega.
    """
    # Tu lógica aquí: llamada a API, DB, etc.
    return {"status": "en camino", ...}
💡

Tip: El docstring es crítico. Gemini lo lee para decidir cuándo usar la tool. Un docstring vago lleva a un agente que usa las tools equivocadas o no las usa cuando debería.

3

Session y Memory

ADK maneja el estado de la conversación en una Session. Cada turno del usuario es un evento que el agente procesa. La historia de la conversación se mantiene automáticamente dentro de la sesión.

4

Multi-agente (opcional)

ADK permite crear arquitecturas donde un agente orquestador delega tareas a agentes especializados. Por ejemplo: un agente raíz que deriva a un agente de envíos, otro de pagos, otro de reclamos.

Orquestador
→
Agente Envíos
→
Agente Pagos
→
Agente Reclamos

🔧 Tipos de tools

ADK soporta varios tipos de herramientas. Las más comunes son las function tools (funciones Python), pero también soporta tools externas y built-ins.

Tipo Cómo se define Cuándo usar
Function Tool Función Python normal APIs internas, lógica de negocio, bases de datos
Built-in Tool Tools de ADK (google_search, code_execution) Búsqueda web, ejecutar código Python
Agent Tool Otro agente ADK como tool Arquitecturas multi-agente, delegar subtareas
ℹ️

ADK convierte automáticamente las funciones Python en JSON Schema para el function calling de Gemini. Los type hints y el docstring con Args/Returns son la documentación que el modelo usa para decidir cómo llamar la tool.

🔄 Ciclo de vida de una consulta

Esto es lo que pasa internamente cada vez que el usuario envía un mensaje:

1

El usuario envía un mensaje

"Quiero saber dónde está mi compra 1234567890"

2

ADK construye el contexto

Arma el prompt completo: system instruction + historial de la conversación + mensaje actual + descripción de las tools disponibles.

3

Gemini razona y decide

El modelo analiza el mensaje y decide si necesita llamar una tool o puede responder directamente. En este caso elige llamar get_shipment_tracking("1234567890").

4

ADK ejecuta la tool

Llama la función Python, obtiene el resultado (diccionario con el estado del envío) y lo agrega al contexto.

5

Gemini genera la respuesta final

Con el resultado de la tool, genera una respuesta en lenguaje natural para el usuario. Si necesita más información, puede llamar otra tool antes de responder.

💡

Este loop de razonar → actuar → observar se llama ReAct (Reasoning + Acting). ADK implementa este patrón automáticamente, vos solo definís las tools y el prompt.

🛠️ Capítulo 2

Agente de atención al cliente de Mercado Libre

Cómo construimos paso a paso un agente de CX real con ADK, incluyendo 9 tools, un sistema de guardrails por prompt y un RAG local con ChromaDB.

🏗️ Arquitectura del proyecto

El proyecto tiene una estructura modular: cada responsabilidad está separada en su propio archivo.

agente_austral_v1/ ├── my_agent/ │ ├── agent.py # Agente principal (root_agent) │ ├── prompt.py # System instruction y guardrails │ ├── tools.py # 9 herramientas de CX │ ├── __init__.py # Expone el agente al ADK runner │ └── rag/ │ ├── knowledge_base.py # Motor RAG (ChromaDB + Gemini embeddings) │ └── documents/ │ ├── garantias.md │ ├── devoluciones.md │ ├── envios.md │ ├── mercado_puntos.md │ └── proteccion_compra.md └── ingest.py # Script de indexación del RAG

📋 Paso a paso: cómo lo construimos

1

Definir el agente base

Arrancamos con el scaffold mínimo de ADK: un Agent con modelo y una instrucción simple. El ADK requiere que el agente principal se llame root_agent y esté en el módulo Python del proyecto.

my_agent/agent.py 
from google.adk.agents import Agent
from .prompt import SYSTEM_INSTRUCTION
from .tools import get_order_status, search_knowledge_base, ...

root_agent = Agent(
    model="gemini-2.5-flash",
    name="meli_customer_service",
    instruction=SYSTEM_INSTRUCTION,
    tools=[get_order_status, get_shipment_tracking, ...],
)
2

Diseñar el system prompt (guardrails)

El prompt es donde viven los guardrails — las reglas de comportamiento del agente. Definimos: personalidad en español argentino, cuándo usar cada tool, cómo manejar quejas, y cuándo escalar a un humano.

⚠️

Los guardrails viven en el prompt. Si el agente rechaza preguntas off-topic (como "¿quién es Ragnarin el bárbaro?"), es porque el prompt lo instruye a comportarse como un asistente de MeLi. Para cambiar ese comportamiento, se modifica el prompt — no hay código que hardcodee esas reglas.

my_agent/prompt.py (extracto) 
SYSTEM_INSTRUCTION = """Sos el asistente virtual de Mercado Libre.
Tu nombre es Meli. Hablás en español argentino.

## Escalamiento
Escalá a un agente humano SOLO si:
- Hay sospecha de fraude
- El usuario pidió hablar con una persona
- El problema no se puede resolver con las tools

## Preguntas fuera de tema
Respondé brevemente y redirigí hacia si necesita
ayuda con alguna compra.
"""
3

Implementar las 9 tools de CX

Cada tool resuelve un caso de uso específico. Son mocks por ahora, pero el contrato (firma, docstring, tipo de retorno) está diseñado para conectar a las APIs reales de Mercado Libre con un cambio mínimo.

ToolQué resuelve
get_order_statusEstado de una compra
get_shipment_trackingSeguimiento de envío
create_return_requestIniciar devolución o cambio
get_return_statusEstado de un reclamo existente
get_payment_statusEstado de un pago Mercado Pago
get_account_summaryNivel, Mercado Puntos, historial
search_knowledge_baseConsulta al RAG local
search_helpFAQ del centro de ayuda
escalate_to_human_agentEscalar casos complejos
4

Agregar el RAG local

Para preguntas que requieren conocimiento específico sobre políticas (plazos exactos, condiciones, excepciones), agregamos un RAG local. Ver la sección siguiente para el detalle.

5

Levantar y probar con adk web

ADK incluye una UI de desarrollo que permite chatear con el agente, ver el historial de tool calls, y guardar conversaciones como eval cases.

terminal 
# Primero indexar los documentos del RAG
python ingest.py

# Levantar la UI de desarrollo
adk web

# O correr en modo terminal
adk run my_agent

🔑 La API key de Google

Antes de poder levantar el agente, necesitás una API key de Google. Una sola key alcanza para todo el proyecto: tanto para el modelo Gemini que razona como para los embeddings del RAG.

Paso 1 — Generarla en Google AI Studio

Andá a aistudio.google.com/apikey, iniciá sesión con cualquier cuenta de Google y hacé clic en "Create API key". Te genera una string del tipo AIzaSyB... de unos 39 caracteres. El tier gratuito permite ~1500 requests/día de Gemini Flash y miles de embeddings — alcanza para experimentar.

Paso 2 — Guardarla en .env

El proyecto espera la key en un archivo my_agent/.env. Su contenido es mínimo:

my_agent/.env 
# NUNCA commitear este archivo — debe estar en .gitignore
GOOGLE_API_KEY=AIzaSyB-tu-key-real-acá
GOOGLE_GENAI_USE_VERTEXAI=FALSE  # usar la API pública de Gemini, no Vertex

Paso 3 — Cómo la lee el código

Hay tres caminos distintos por los que la key llega al runtime, dependiendo de qué pieza la necesite:

ClienteCómo carga la key
ADK web/run Detecta automáticamente .env al lado del agente. Por eso agent.py nunca menciona la key — ADK la inyecta como variable de entorno antes de instanciar el modelo.
knowledge_base.py Como crea su propio cliente genai.Client para los embeddings, lee la key explícitamente con os.environ.get("GOOGLE_API_KEY") y lanza EnvironmentError si falta.
ingest.py Es un script standalone (no se ejecuta a través de ADK), así que carga el .env manualmente con load_dotenv() de la librería python-dotenv.
my_agent/rag/knowledge_base.py (extracto) 
def _get_genai_client() -> genai.Client:
    api_key = os.environ.get("GOOGLE_API_KEY")
    if not api_key:
        raise EnvironmentError("GOOGLE_API_KEY no está configurada en el entorno.")
    return genai.Client(api_key=api_key)
⚠️

Buenas prácticas de seguridad — no negociables:

  • El .env nunca se commitea. Tiene que estar en .gitignore desde el día cero.
  • En su lugar, subí un .env.example con GOOGLE_API_KEY=tu_key_aca (sin el valor real) para que otros sepan qué variables necesitan.
  • Si subiste una key por accidente a GitHub: revocala ya en AI Studio y generá una nueva. Los bots escanean repos públicos en minutos.
  • En producción no se usa .env: se inyectan las keys via Secret Manager (AWS/GCP), variables de entorno del runtime (Cloud Run, Vercel), o sistemas dedicados como Vault.
  • Si la app tiene varios servicios, idealmente cada uno tiene su propia key, así podés revocarlas por separado y auditar uso.

🔍 RAG local: cómo funciona

RAG (Retrieval-Augmented Generation) permite que el agente consulte una base de conocimiento propia antes de responder preguntas específicas sobre políticas.

Usuario pregunta
"¿cuánto tarda el reintegro?"
→
Agente llama
search_knowledge_base()
→
ChromaDB
busca por similitud
Responde con
información precisa
←
Gemini sintetiza
los chunks relevantes
←
Devuelve chunks
con score de similitud

La búsqueda es semántica (por significado), no por palabras clave exactas.

A

Indexación (una sola vez)

Se corren los documentos .md de la carpeta documents/, se dividen en chunks de ~400 palabras, se les calculan embeddings con gemini-embedding-001 y se guardan en ChromaDB de forma persistente en disco.

terminal 
$ python ingest.py
Indexando documentos...
Listo. 6 chunks indexados en chroma_db/
B

Búsqueda en runtime

Cuando el agente necesita info específica, llama search_knowledge_base("query"). La función genera un embedding de la query, lo compara contra todos los chunks en ChromaDB por similitud coseno, y devuelve los 3 más relevantes.

C

Agregar nuevo conocimiento

Solo hace falta soltar un nuevo .md en documents/ y volver a correr python ingest.py. El índice se reconstruye automáticamente.

💡

Para conectar a APIs reales de Mercado Libre: reemplazá los return {...} de mocks en tools.py por llamadas HTTP a los endpoints de la API de ML. El contrato del agente (nombre, parámetros, docstring) no cambia.

✅ Evals: cómo testear el agente

ADK incluye un sistema de evaluación que verifica automáticamente que el agente se comporta correctamente. Hay dos cosas que evalúa:

🔧

Tool use correcto

Verifica que el agente llamó las tools esperadas para cada consulta. Si el usuario pregunta por el estado de un envío, el eval chequea que se llamó get_shipment_tracking.

💬

Calidad de respuesta

Compara la respuesta del agente contra una respuesta de referencia usando similitud semántica. Tolera variaciones en el lenguaje — busca que el significado sea correcto, no las palabras exactas.

terminal — correr evals 
# Correr el eval set contra el agente
adk eval my_agent my_agent/eval_set_1.evalset.json

# Output esperado:
✓ caso_devolucion_basica         PASS  (tool: create_return_request ✓)
✓ consulta_estado_envio           PASS  (tool: get_shipment_tracking ✓)
✗ pregunta_garantia_especifica    FAIL  (respuesta: 0.61 < umbral 0.70)
ℹ️

El eval set (eval_set_1.evalset.json) se puede poblar directamente desde la UI de adk web guardando conversaciones reales como casos de prueba — sin escribir JSON a mano.
