01

¿Qué es un agente?

Un LLM por sí solo solo sabe generar texto. Un agente además puede actuar sobre el mundo.

Chatbot vs Agente

La diferencia clave: capacidad de actuar

💬 Chatbot tradicional

  • Input: texto del usuario
  • Output: texto generado
  • No tiene acceso a datos reales
  • Inventa información si no sabe
  • Stateless: olvida todo entre mensajes
Limitación: "¿En qué materias estoy inscripto?" → "No tengo acceso al sistema académico del ITBA."

🤖 Agente con tools

  • Input: texto del usuario
  • Decide qué tool ejecutar
  • Llama a APIs, bases de datos, sistemas reales
  • Razona con datos verídicos
  • Mantiene memoria de la sesión
Ada: "¿Cuándo cursa Algoritmos?" → busca en el RAG → "Algoritmos (INFO-201) se cursa en 3er cuatrimestre…"

02

Google ADK

El framework que nos resuelve toda la "plomería" de construir un agente.

¿Qué es Google ADK?

Agent Development Kit — el SDK oficial de Google para construir agentes

ADK es un framework de Google que abstrae los componentes complejos de construir un agente, dejándote escribir solo la lógica de negocio. Está disponible en Python, Java, Go y TypeScript — en este proyecto usamos la versión Python.

📖 Docs oficiales: adk.dev/get-started

Lo que nos resuelve ADK

ComponenteLo que hace por vos
AgentEncapsula modelo + prompt + tools + configuración de seguridad
OrquestadorLoop: usuario → LLM → ¿tool? → ejecutar → LLM → respuesta
Function callingConvierte funciones Python en JSON schemas automáticamente
SessionsMantiene el historial de conversación (en memoria o persistido)
adk webUI web lista para probar el agente, con trace de tool calls
Eval setsSistema de evaluación con casos de prueba
Versión usada: ADK 1.32.0 con Python 3.12 y el SDK google-genai para los embeddings.

Definiendo un agente en ADK

El archivo agent.py de Ada — el "manifiesto" del agente
from google.adk.agents.llm_agent import Agent
from google.genai.types import GenerateContentConfig, SafetySetting, HarmCategory

from .prompt import SYSTEM_INSTRUCTION
from .tools import (
    enroll_in_subject,
    escalate_to_academic_advisor,

root_agent = Agent(
    model="gemini-2.5-flash",        # el LLM
    name="itba_academic_assistant",
    description="Asistente académico virtual del ITBA.",
    instruction=SYSTEM_INSTRUCTION,    # el system prompt

Eso es todo. ADK toma esas funciones Python, lee sus docstrings, infiere los tipos y construye los JSON schemas que el LLM necesita. Cero boilerplate.

03

El orquestador

El "director de orquesta" que ADK provee out of the box.

El loop del orquestador

Lo que pasa entre tu input y la respuesta del agente
1
Recibe el input del usuario "Quiero anotarme en Algoritmos, mi legajo es 12345"
2
Arma el contexto Junta el system prompt + historial de la sesión + el nuevo mensaje + schemas de las tools disponibles.
3
Manda todo al LLM Gemini procesa y devuelve: o bien un texto final, o bien una function call con nombre de tool y argumentos.
4
Si hay function call: ejecuta la tool Llama a la función Python con los argumentos que el LLM pidió. Captura el resultado (un dict).
5
Devuelve el resultado al LLM Le inyecta el output de la tool como nuevo turno de contexto, y vuelve al paso 3.
6
Cuando el LLM responde con texto final → al usuario El orquestador termina el ciclo y persiste todo en la sesión.
Este loop puede iterar varias veces. El LLM puede llamar a 1, 2, 5 tools en cadena antes de responder al usuario. Por ejemplo: primero buscar el código de la materia con search_knowledge_base, después inscribir con enroll_in_subject.

El system prompt: la personalidad de Ada

Archivo prompt.py — define quién es, qué hace y cómo

El system prompt es el primer mensaje que ve el LLM en cada conversación. Define el comportamiento del agente. Fragmento real del prompt de Ada:

# prompt.py

SYSTEM_INSTRUCTION = """Sos **Ada**, el asistente académico virtual del
**ITBA (Instituto Tecnológico de Buenos Aires)**.

## Tu personalidad
- Hablás en español argentino (vos, sos, tenés).
- Sos claro y conciso.

## Inscripciones
Para inscribir a un alumno necesitás obligatoriamente:
- Legajo del alumno
- Código de materia (ej: INFO-201)
- Nombre de la materia

Flujo correcto:
1. Si el alumno menciona una materia pero no su código,
   buscalo en `search_knowledge_base` primero.
2. Confirmá los datos antes de ejecutar la inscripción.
3. Usá `enroll_in_subject` para inscribir.

## Reglas
- **Nunca** inventes códigos de materias.
- **Nunca** inscribas sin legajo confirmado.
"""
Lección de diseño: el system prompt no es solo "tono". Es donde codificás las reglas de negocio que el LLM debe seguir. Acá decidimos que nunca debe inscribir sin legajo.
04

Tools: cómo el LLM actúa

Funciones Python comunes que el LLM puede invocar mediante function calling.

Anatomía de una tool

Una función Python "normal" que ADK convierte automáticamente
def enroll_in_subject(student_id: str, subject_code: str, subject_name: str) -> dict:
    """Inscribe a un alumno en una materia. Verifica primero si ya está inscripto;
    si no lo está, realiza la inscripción y la persiste en la base de datos.

    Args:
        student_id: Legajo o DNI del alumno (ej: 12345 o 40123456).
        subject_code: Código de la materia (ej: INFO-201).
        subject_name: Nombre completo de la materia.

    Returns:
        Resultado de la inscripción: éxito, ya inscripto, o error.
    """
    if db.is_enrolled(student_id, subject_code):
        return {"success": False, "already_enrolled": True, ...}

    record = db.enroll(student_id, subject_code, subject_name)
    return {"success": True, **record, "message": "Inscripción exitosa..."}
📝

Docstring

Se convierte en la descripción para el LLM. Es lo que el LLM lee para decidir si usar la tool.

🏷️

Type hints

Definen el JSON schema de los parámetros. str → string, int → integer, etc.

📤

Return dict

El dict que retornás se le inyecta al LLM como contexto para que arme la respuesta final.

Las 5 tools de Ada

Catálogo completo de herramientas del agente
🔍
search_knowledge_base(query)
Búsqueda semántica en la base de conocimiento

Busca en ChromaDB los 3 fragmentos más relevantes de los documentos del ITBA. Devuelve título, fuente, contenido y score de relevancia. Lectura — sin efectos.

✍️

Inscribe a un alumno en una materia

📋

👥

Query a SQLite filtrando por código de materia. Útil para roles administrativos.

🆘

Deriva a un asesor humano

Genera un ticket ITBA-XXXXX con tiempo de respuesta estimado. Para casos que el agente no puede resolver solo.

05

RAG: la base de conocimiento

Cómo Ada "lee" los planes de estudio del ITBA antes de responder.

¿Qué es RAG?

Retrieval-Augmented Generation

Los LLMs tienen un conocimiento general, pero no saben nada del ITBA en particular. RAG es la técnica de inyectarle al LLM información específica recuperada de una base de documentos, justo cuando la necesita.

❌ Sin RAG

¿Qué cursa Algoritmos en el ITBA?
No tengo información actualizada sobre el plan de estudios del ITBA. Te recomiendo consultar el sitio oficial...

✅ Con RAG

¿Qué cursa Algoritmos en el ITBA?
search_knowledge_base("Algoritmos correlativas ITBA")
Algoritmos (INFO-201) se cursa en 3er cuatrimestre. Sus correlativas son INFO-103 (Introducción a la Programación) aprobada y INFO-106 (Análisis Matemático II) regularizada.
Por qué funciona: el LLM no "memoriza" los planes de estudio. Los recibe como contexto en cada consulta, y los razona en el momento. Esto evita alucinaciones y permite actualizar la información sin re-entrenar nada.

El pipeline RAG en dos fases

Indexación (offline) y búsqueda (online)

🛠️ Fase 1: Indexación — corre una sola vez con python ingest.py

1
Lee los 5 docs Markdown de my_agent/rag/documents/: carreras, planes de informática, industrial, electrónica, admisión.
2
Chunking: divide cada doc en pedazos de 400 palabras con 50 de overlap. Esto evita que se pierda contexto entre chunks vecinos.
3
Embedding: cada chunk se manda al modelo gemini-embedding-001, que devuelve un vector numérico de alta dimensión que "captura" su significado.
4
Almacenamiento: los vectores + textos + metadata (fuente, título) se guardan en ChromaDB, un vector store local (sqlite-based).
Resultado: 5 documentos → 10 chunks indexados en my_agent/rag/chroma_db/.

Fase 2: Búsqueda en tiempo real

Cada vez que el LLM llama a search_knowledge_base(query)
1
El LLM decide buscar. Pasa una query en lenguaje natural, ej: "correlativas algoritmos informática".
2
Embedding de la query. Se transforma en el mismo espacio vectorial que los chunks indexados (con task_type="RETRIEVAL_QUERY").
3
Similitud coseno. ChromaDB compara el vector de la query contra todos los vectores indexados y devuelve los 3 más similares.
4
Devolución al LLM. La tool retorna un dict con título, fuente, contenido y score de cada chunk. El LLM lo lee y arma su respuesta. 
# rag/knowledge_base.py — fragmento clave

def search(query: str, n_results: int = 3) -> list[dict]:
    query_embedding = genai_client.models.embed_content(
        model="gemini-embedding-001",
        contents=query,
        config=EmbedContentConfig(task_type="RETRIEVAL_QUERY"),
    ).embeddings[0].values

    results = collection.query(
        query_embeddings=[query_embedding],
        n_results=n_results,
        include=["documents", "metadatas", "distances"],
    )
    return [...]  # [{text, source, title, relevance_score}, ...]

¿Por qué similitud coseno?

La métrica detrás de la búsqueda semántica

Los embeddings son vectores en un espacio de alta dimensión (3072 dimensiones en gemini-embedding-001). Para comparar dos textos no nos interesa qué tan lejos están esos vectores, sino en qué dirección apuntan. La similitud coseno mide exactamente eso: el ángulo entre dos vectores.

La fórmula

# Coseno del ángulo entre los vectores A y B
cos(θ) = (A · B) / (‖A‖ × ‖B‖)
           ▲              ▲
           producto       magnitudes
           punto          (longitud de cada vector)

Intuición geométrica

Ángulocos(θ)Significado semántico
0°1.0Vectores idénticos → mismo significado
25°0.9Muy relacionados, contexto similar
90°0.0Ortogonales → conceptos independientes
180°-1.0Direcciones opuestas → significados antagónicos
¿Por qué no distancia euclidiana? Porque las frases "perro" y "perro grande blanco peludo y juguetón" tienen la misma dirección semántica pero distinta magnitud (el segundo texto produce un vector más largo). El coseno ignora la magnitud y se enfoca solo en la dirección — exactamente lo que queremos para medir similitud de significado.

En el código de Ada

# rag/knowledge_base.py — al crear la colección de ChromaDB
collection = client.create_collection(
    name="itba_knowledge",
    metadata={"hnsw:space": "cosine"},  # ← métrica usada
)

# ChromaDB devuelve "distance" (1 - cos), por eso lo invertimos:
relevance_score = round(1 - dist, 3)  # cosine distance → similarity

Persistencia con SQLite

Cómo guardamos las inscripciones reales (sin servidor, sin configuración).

El esquema de inscripciones

Archivo my_agent/inscripciones.db — se crea automáticamente
# db.py — schema de la tabla

def _init_db(conn: sqlite3.Connection) -> None:
    conn.execute("""
        CREATE TABLE IF NOT EXISTS inscripciones (
            id              INTEGER PRIMARY KEY AUTOINCREMENT,
            student_id      TEXT NOT NULL,
            subject_code    TEXT NOT NULL,
            subject_name    TEXT NOT NULL,
            inscripto_en    TEXT NOT NULL,
            UNIQUE(student_id, subject_code)
        )
    """)
    conn.commit()
El secreto: el constraint UNIQUE(student_id, subject_code). Hace que sea físicamente imposible duplicar inscripciones a nivel de base de datos, sin importar lo que haga el agente.

Las 3 operaciones que expone db.py

FunciónHace
is_enrolled(student_id, code)SELECT 1 → devuelve True o False
enroll(student_id, code, name)INSERT con timestamp ISO
get_enrollments(student_id)SELECT * filtrando por alumno
get_subject_enrollments(code)SELECT * filtrando por materia

Defensa en dos capas → idempotencia

Cómo enroll_in_subject evita inscripciones duplicadas

Idempotencia = ejecutar la misma operación N veces tiene el mismo efecto que ejecutarla una sola vez. Llamar 10 veces a "anotame en Videojuegos" debe dejar al alumno anotado una sola vez, no diez.

🛡️ Chequeo #1 — en Python (tools.py)

Para experiencia de usuario: si ya está anotado, responde amablemente sin tirar error.

def enroll_in_subject(student_id, subject_code, subject_name) -> dict:
    if db.is_enrolled(student_id, subject_code):    # ← CHEQUEO 1
        return {"success": False, "already_enrolled": True,
                "message": f"Ya estás inscripto en {subject_name}."}

    record = db.enroll(student_id, subject_code, subject_name)
    return {"success": True, **record}

🛡️ Chequeo #2 — en SQLite (db.py)

Para integridad de datos: red de seguridad contra race conditions (dos requests simultáneos que pasen el chequeo #1 a la vez).

CREATE TABLE IF NOT EXISTS inscripciones (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    student_id      TEXT NOT NULL,
    subject_code    TEXT NOT NULL,
    subject_name    TEXT NOT NULL,
    inscripto_en    TEXT NOT NULL,
    UNIQUE(student_id, subject_code)    -- ← CHEQUEO 2
)
¿Por qué dos capas y no una? El chequeo de Python solo no alcanza: si dos requests llegan al mismo tiempo, ambos pueden ver is_enrolled = False y los dos insertarían. El UNIQUE de SQL solo tampoco alcanza: el usuario vería un error técnico horrible. Juntos = robustos y amigables.

Función calling: cómo el LLM "llama" a una tool

El protocolo detrás de las llamadas a tools

El LLM nunca ejecuta código. Solo emite un mensaje estructurado pidiendo que se ejecute. ADK lo intercepta, ejecuta la función, y le devuelve el resultado.

Lo que devuelve el LLM cuando quiere llamar una tool:

{
  "tool_calls": [
    {
      "name": "enroll_in_subject",
      "arguments": {
        "student_id": "39071",
        "subject_code": "INFO-410",
        "subject_name": "Videojuegos"
      }
    }
  ]
}

Lo que ADK le inyecta de vuelta al LLM:

{
  "role": "tool",
  "name": "enroll_in_subject",
  "content": {
    "success": true,
    "student_id": "39071",
    "subject_code": "INFO-410",
    "inscripto_en": "14/05/2026 14:52",
    "message": "Inscripción exitosa en Videojuegos (INFO-410)."
  }
}
Esto es todo el "truco": el LLM y el código se comunican vía JSON estructurado. ADK abstrae todo el manejo del protocolo, los reintentos, el parseo y la inyección de resultados.
